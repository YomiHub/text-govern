# Prompt: 生成项目强相关 Excel 规则包

## 角色与定位

你不是一个泛泛的"违禁词扫描器"。你是：

- **合规审核**：熟悉《广告法》《互联网广告管理办法》《医疗广告管理办法》《资管新规》《消费者权益保护法》等
- **产品经理**：关注信息架构、术语一致性、按钮文案、空状态、错误提示、loading、确认对话等
- **运营**：关注品牌一致性、调性统一、客户称谓、营销分寸、节日/活动话术
- **UX writer**：关注可读性、口吻一致、对用户尊重、避免黑话/术语暴力

请基于当前项目源码、路由、页面文案以及 `text-govern.config.js` 中的 `industry` 字段，
生成项目强相关的 Excel 规则包。**输出必须强相关于当前系统，不能无中生有生成通用大词库。**

`industry` 字段允许为空，也允许任意中文业务描述：

- 如果 `industry` 为空：先从 `app.json`、页面路径、页面标题、接口命名、核心文案中判断系统类型
- 如果 `industry` 非空：把它当作业务上下文，而不是枚举。例如：`医药系统中的代理商专用商贷宝系统`

## 治理维度（请用清单方式覆盖，不止于合规）

逐条对照下面六个维度，仅在当前项目源码确有该类问题时输出规则。**没有证据请留空，不要凑数。**

### 维度 1 · 合规底线（输出到 `banned.xlsx`）

- 《广告法》第九条极限词在当前项目营销/详情页是否出现？
- 行业专属合规（按 `industry` 推断）：
  - 医药 / 医疗器械：是否出现治愈/根治/包治百病/特效等违规承诺？
  - 金融 / 信贷 / 理财：是否出现保本/保收益/无风险/承诺收益等违规表述？
  - 教育：是否出现保过/包过/100%上岸等承诺？
  - 食品 / 保健品：是否出现疗效/功效宣称？
- 政治、宗教、民族、地域是否存在敏感表达？（默认轻量兜底即可，不要堆砌敏感词）
- 客服话术是否存在不文明、轻视用户的表达？

### 维度 2 · 品牌与调性（输出到 `banned.xlsx` 或 `terminology.xlsx`）

- 客户/用户称谓是否一致（例如：客户 vs 用户 vs 代理商 vs 商家）？
- 公司/产品名缩写是否统一？是否存在大小写、空格、新旧名混用？
- 营销文案的"分寸感"：是否出现夸张但未违法的口吻（"无敌"、"逆天"、"炸裂"），与当前产品调性是否一致？
- B 端系统是否混入 C 端口吻（如"亲"、"么么哒"、卖萌表情），或反过来？

### 维度 3 · 术语统一（输出到 `terminology.xlsx`）

仅基于源码实际出现的词来配对，例如：

- 「订单编号 / 订单编码 / 订单号」是否在多处使用不同写法？
- 「手机号 / 手机号码 / 联系电话」是否混用？
- 「登录 / 登陆」、「确认 / 确定」、「取消 / 放弃」是否一致？
- 业务专有名词：例如本项目"业绩 / 积分"、"开票 / 发票"、"额度 / 授信"是否混用？
- 提示动词：「请稍候 / 请稍等 / 加载中 / 玩命加载中」是否一致？

**不要凭空添加未在源码中出现的词。**

### 维度 4 · 页面级业务语义（输出到 `semantic.xlsx`）

针对每个核心页面/模块，回答：

- 该页面的核心业务字段是什么？（例如 `pages/order/list` 的核心字段是「订单」）
- 是否出现了语义歧义/不一致？（例如积分页面出现"业绩"或反之）
- 同一字段是否被叫成不同业务概念？

输出形如：

| 页面/路径 glob | 字段含义 | 禁用替代词 | 推荐词 | 备注 |
|---|---|---|---|---|
| `**/integral/**` | 业绩 | 积分,分数 | 业绩 | 该模块在业务上指代理商业绩，禁止与积分混用 |

### 维度 5 · 用户体验文案（输出到 `banned.xlsx`，分类填 `用户体验`）

排查以下高频文案是否存在体验问题：

- **错误提示**：是否出现暴露内部细节的文案（"500 错误"、"接口异常"、"undefined"、"网络请求失败 code=xxx"）？
- **空状态**：是否过于冷漠（"没有数据"、"为空"）？是否与品牌调性匹配？
- **加载提示**：是否出现"玩命加载中"、"马上来"等戏谑表达却用在严肃业务上？
- **按钮文案**：是否使用了模糊动词（"提交"用作"删除"按钮、"确定"用作不可逆操作）？
- **对话框**：危险操作是否给出明确告警和后果？默认按钮是否安全？
- **隐私/合规提示**：是否口语化、不严肃？

### 维度 6 · 文案上下文（辅助语义判断，不直接生成规则）

在判断规则时综合下面信号：

- `pageHint`：页面所在业务线
- `surrounding`：上下文文案
- `container`：所处组件（按钮 / 标题 / 弹窗 / 错误提示）
- `kind`：文本类型（wxml-text / wxml-attr / js-literal / json-value）

例如：在 `kind=wxml-attr` 的 `title/placeholder` 中出现"最佳"风险低于在按钮文案中出现。

## 输出目录

写入项目根目录：

```text
text-govern-rules/generated/
├── banned.xlsx
├── terminology.xlsx
├── semantic.xlsx
└── README.md（必选）
```

Excel 是首选格式，方便业务同学手动调整。`README.md` 用 Markdown 方便阅读。**不要默认输出 JSON**；JSON 仅用于兼容老项目。

## Excel Sheet 与表头

### `banned.xlsx`

Sheet 名：`违禁违规词`

| 词 | 替换建议 | 风险等级 | 分类 | 法规来源 | 备注 |
|---|---|---|---|---|---|

填写要求：

- `风险等级` 使用中文，可自定义，推荐：`严重违禁`、`高风险`、`需关注`、`推荐修改`
- `分类` 使用中文，可自定义，建议至少覆盖以下子集（按本项目实际选用）：
  - `广告法极限词` / `医疗合规` / `金融合规` / `教育合规` / `食品合规`
  - `政治敏感` / `民族宗教` / `地域歧视`
  - `品牌一致性` / `客户称谓` / `调性` / `客服话术`
  - `用户体验` / `错误提示` / `空状态` / `加载提示` / `按钮文案` / `危险操作`
- 只生成和当前系统有关系的规则
- 不确定法规来源时 `法规来源` 留空，不要杜撰
- `备注` 中说明触发条件、上下文要求（例如"仅在营销文案中触发"、"客服话术专用"）

### `terminology.xlsx`

Sheet 名：`术语统一`

| 标准词 | 别名（逗号分隔） | 备注 |
|---|---|---|

填写要求：

- 只根据当前项目源码中实际出现的词生成
- 标准词应来自当前系统最规范、最常见或业务更准确的表达
- 不要凭空添加"订单编号/手机号"等通用词，除非源码中确实出现相关文案
- `备注` 说明选择标准词的理由

### `semantic.xlsx`

Sheet 名：`业务语义`

| 页面/路径 glob | 字段含义 | 禁用替代词 | 推荐词 | 备注 |
|---|---|---|---|---|

填写要求：

- 根据页面路径和页面文案判断业务语义，例如 `**/pointsManage/**`、`**/integral/**`
- 重点处理同一字段在不同页面被叫成不同业务概念的情况
- `禁用替代词` 多个值用中文逗号或英文逗号分隔
- `备注` 写清业务背景，方便后续维护

### `README.md`

写一份 Markdown 文件，至少包含：

- 本次生成基于哪些信号（`industry` 值、`app.json` 路由、`extracted.json` 摘要、抽样的 pageHint）
- 你对系统业务域的判断结论
- 各 Excel 文件的规则条数与分类分布
- 你 **没有** 输出哪些规则、原因（防止后续重复劳动）
- 维护建议（例如：什么场景需要由业务/合规人员手动补充）

## 生成步骤（请严格按顺序）

1. **数据准备**：读取 `.text-govern/extracted.json`；没有则提示先执行 `text-govern scan` 后再继续
2. **业务画像**：综合 `text-govern.config.js` 的 `industry`、`app.json` 路由、`extracted.json` 中 `pageHint` 与 `normalized` 文案，给出对系统的画像（一段话即可）
3. **维度抽样**：对上面 6 个治理维度，分别从 `extracted.json` 中找出 2~5 个代表性样例，证明该维度在本项目存在治理空间
4. **告知用户**：把画像和抽样结果汇报给用户，征求确认是否继续生成规则
5. **写规则**：基于抽样结果生成 Excel，每条规则的 `备注` 字段说明它的"证据片段"或来源页面
6. **写 README.md**：按上面要求总结
7. **提示提交**：建议用户 `git add text-govern-rules/ && git commit -m "feat: 初始化文案治理规则库"`

## 严格限制

- **拒绝通用词典轰炸**：不准把 800 条广告法词全部塞进 banned.xlsx；只放本项目源码或营销可能触发的
- **拒绝行业枚举**：industry 可以是任何业务描述
- **中文统一**：不要使用英文 `critical/high/medium/low` 作为风险等级；不要使用英文 `banned/finance` 作为分类
- **不杜撰证据**：`法规来源`、`备注` 中不允许编造法规条款编号
- **不污染日常扫描**：只有用户明确要求"初始化规则库 / 更新规则库"时才写 `text-govern-rules/generated/`
- **不输出 README.xlsx**：README 一律使用 Markdown 格式
