# Prompt: 生成项目强相关 Excel 规则包

## 分类模型（必须了解并严格遵守）

本工具采用**四大固定大类 + AI 自主识别子类**的模型：

| 大类（category，固定不变） | 含义 | `分类` 列填写规则 |
|---|---|---|
| `行业合规` | 违反适用法规、行业强制要求 | **由你按系统类型自主决定子类名称**，例如：某行业功效宣称 / 绝对化用语 / 保本承诺 / 许可证合规 … |
| `业务语义统一类` | 跨页面字段表述不一致 | 按业务字段自定义，例如：积分/业绩混用 |
| `词义统一类` | 同一概念多种写法混用 | 按术语对命名 |
| `优化类` | 不违规但措辞可改进 | 按场景命名，例如：错误提示 / 按钮文案 |

> **`分类` 列的值对应"大类"下的子类**，自由填写中文，不得使用英文。
> `行业合规` 的子类完全由你根据项目行业与适用法规决定，**不写死任何特定法规或行业**。
> Excel `分类` 列的自定义值会透传到报告，按实际情况填写即可。

## 角色与定位

你不是一个泛泛的"违禁词扫描器"，也不是规则词典的搬运工。你同时扮演四个角色：

- **合规审核员**：你需要**自行判断**本项目在中国大陆公开发布涉及哪些合规范围，不局限于任何预设清单。下方列举的法规仅为示例参考，你必须根据项目落地形态、受众、功能模块扩展或裁剪。
- **产品经理**：关注信息架构、术语一致性、按钮文案、空状态、错误提示、loading、确认对话等。
- **运营**：关注品牌一致性、调性统一、客户称谓、营销分寸、节日/活动话术。
- **UX writer**：关注可读性、口吻一致、对用户尊重、避免黑话/术语暴力。

请基于当前项目源码、路由、页面文案以及 `text-govern.config.js` 中的 `industry` 字段，
生成项目强相关的 Excel 规则包。**输出必须强相关于当前系统，不能无中生有生成通用大词库。**

`industry` 字段允许为空，也允许任意中文业务描述：

- 如果 `industry` 为空：先从 `app.json`、页面路径、页面标题、接口命名、核心文案中判断系统类型
- 如果 `industry` 非空：把它当作业务上下文，而不是枚举。例如：`医院信息系统`

### 维度 2 · 品牌与调性（输出到 `banned.xlsx` 或 `terminology.xlsx`）

- 客户/用户称谓是否一致（例如：客户 vs 用户 vs 代理商 vs 商家）？
- 公司/产品名缩写是否统一？是否存在大小写、空格、新旧名混用？
- 营销文案的"分寸感"：是否出现夸张但未违法的口吻（"无敌"、"逆天"、"炸裂"），与当前产品调性是否一致？
- B 端系统是否混入 C 端口吻（如"亲"、"么么哒"、卖萌表情），或反过来？

### 维度 3 · 术语统一（输出到 `terminology.xlsx`）

仅基于源码实际出现的词来配对，例如：

- 「订单编号 / 订单编码 / 订单号」是否在多处使用不同写法？
- 「手机号 / 手机号码 / 联系电话」是否混用？
- 「登录 / 登陆」、「确认 / 确定」、「取消 / 放弃」是否一致？
- 业务专有名词：例如本项目"业绩 / 积分"、"开票 / 发票"、"额度 / 授信"是否混用？
- 提示动词：「请稍候 / 请稍等 / 加载中 / 玩命加载中」是否一致？

**不要凭空添加未在源码中出现的词。**

### 维度 4 · 页面级业务语义（输出到 `semantic.xlsx`）

针对每个核心页面/模块，回答：

- 该页面的核心业务字段是什么？（例如 `pages/order/list` 的核心字段是「订单」）
- 是否出现了语义歧义/不一致？（例如积分页面出现"业绩"或反之）
- 同一字段是否被叫成不同业务概念？

输出形如：

| 页面/路径 glob | 字段含义 | 禁用替代词 | 推荐词 | 备注 |
|---|---|---|---|---|
| `**/integral/**` | 业绩 | 积分,分数 | 业绩 | 该模块在业务上指代理商业绩，禁止与积分混用 |

### 维度 5 · 用户体验文案（输出到 `banned.xlsx`，分类填 `用户体验`）

排查以下高频文案是否存在体验问题：

- **错误提示**：是否出现暴露内部细节的文案（"500 错误"、"接口异常"、"undefined"、"网络请求失败 code=xxx"）？
- **空状态**：是否过于冷漠（"没有数据"、"为空"）？是否与品牌调性匹配？
- **加载提示**：是否出现"玩命加载中"、"马上来"等戏谑表达却用在严肃业务上？
- **按钮文案**：是否使用了模糊动词（"提交"用作"删除"按钮、"确定"用作不可逆操作）？
- **对话框**：危险操作是否给出明确告警和后果？默认按钮是否安全？
- **隐私/合规提示**：是否口语化、不严肃？

### 维度 6 · 文案上下文（辅助语义判断，不直接生成规则）

在判断规则时综合下面信号：

- `pageHint`：页面所在业务线
- `surrounding`：上下文文案
- `container`：所处组件（按钮 / 标题 / 弹窗 / 错误提示）
- `kind`：文本类型（wxml-text / wxml-attr / js-literal / json-value）

例如：在 `kind=wxml-attr` 的 `title/placeholder` 中出现"最佳"风险低于在按钮文案中出现。

## 生成步骤（请严格按顺序）

1. **数据准备**：读取 `.text-govern/extracted.json`；没有则提示先执行 `text-govern scan` 后再继续
2. **业务画像**：综合 `text-govern.config.js` 的 `industry`、`app.json` 路由、`extracted.json` 中 `pageHint` 与 `normalized` 文案，**完成维度 1 的第一步和第二步**（判断落地形态与适用合规范围），给出系统画像
3. **维度抽样**：对上面 6 个治理维度，分别从 `extracted.json` 中找出 2~5 个代表性样例，证明该维度在本项目存在治理空间
4. **告知用户**：把画像（含判定的合规范围）和抽样结果汇报给用户，征求确认是否继续生成规则
5. **写规则**：基于抽样结果生成 Excel，每条规则的 `备注` 字段说明它的"证据片段"或来源页面；遵守数量上限（见严格限制）
6. **写 README.md**：按上面要求总结
7. **提示提交**：建议用户 `git add text-govern-rules/ && git commit -m "feat: 初始化规则库"`

## 严格限制

- **拒绝通用词典轰炸**：不准把任何大词库全部塞进 banned.xlsx；只放本项目源码或营销可能触发的证据词条
- **拒绝行业枚举**：industry 可以是任何业务描述，不要枚举固定行业分类
- **中文统一**：不要使用英文 `critical/high/medium/low` 作为风险等级；不要使用英文 `banned/finance` 作为分类
- **不杜撰证据**：`法规来源`、`备注` 中不允许编造法规条款编号
- **不污染日常扫描**：只有用户明确要求"初始化规则库 / 更新规则库"时才写 `text-govern-rules/generated/`
- **不输出 README.xlsx**：README 一律使用 Markdown 格式
- **不输出统计表**：禁止生成词频统计、词汇出现次数等任何与规则匹配无关的 Sheet 或列
- **产出后必须运行 `TG_CMD rules:verify`**：退出码非 0 禁止汇报成功，将错误原文完整返给用户后修正重跑
- **维度 1 的法规清单是示例，AI 必须根据项目实际形态自行扩展，不应缺漏适用法规**
- **基线类目规则**：当 `rules.includeDefaults = false` 时，**禁止**生成色情/政治/暴恐/涉枪涉爆/广告违规等基线类目词条；当 `rules.includeDefaults = true` 时，按维度 1「内置基线类目限定范围」扫代码库，**只输出有证据的命中词，不照抄词库文件，不堆砌通用词**

### 数量上限（按重要程度排序后截断）

规则排序原则：合规底线 > 品牌一致 > 术语统一 > 用户体验；同等级内按源码命中证据数量降序。

| 文件 | 风险等级 | 最大条数 |
